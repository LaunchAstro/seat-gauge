# Session log

The Log tab publishes `log.json` in the app's Application Support folder, beside `machines.json` and `headroom.json`. It polls the configured machines every 30 seconds. `seatgauge-cli log` runs one round and prints the same snapshot.

## Requirements

The Log tab sees only agents that run inside herdr, a terminal workspace manager that runs agent sessions in named workspaces and panes and answers questions about them on the command line. Each machine the tab reads needs herdr at `~/.local/bin/herdr`; the probe looks nowhere else. On this Mac without it, the tab lists no sessions and shows that machine's line as "the Log tab reads agent sessions from herdr, and herdr was not found at ~/.local/bin/herdr". A remote machine without it shows the helper line below, "the Log probe did not answer; install this version's CLI helper on the machine", because the tab cannot tell the two apart over SSH. The other tabs do not need herdr.

The repo, section and seat columns come from the workspace's name, which must read `<repo>-<section>-<seat>`, such as `seat-gauge-Log-work`. Any other name still logs the session, with those three fields empty; the tab shows them as "unlabelled repo", "no section" and "no seat".

## Rows

Each row is keyed by `machine` and `session_id`. It carries workspace and pane, tool, model and effort, repo, section, seat, branch, repository, `started_at`, `closed_at`, status, `as_of`, `stale`, token counts, counts by model, and list-price USD. Workspace labels split from the right as `<repo>-<section>-<seat>`. A label without three parts leaves those fields empty. A model with no known price leaves the price empty.

`repo` is the workspace label's first part, a name you chose. `repository` is the GitHub `owner/name` of the folder the session works in, as its `origin` remote spells it, before any `insteadOf` setting rewrites it, such as `LaunchAstro/seat-gauge`, from an `https://`, `http://`, `ssh://` or `git://` remote on github.com with no port but its protocol's own and no query or fragment, or the short SSH form `github.com:<owner>/<name>`, with or without a user name before it; or null when there is none: the folder is not in a repository, has no `origin`, its `origin` is not on github.com, git did not answer, or the folder is on a mounted volume or otherwise one git may not read (empty or relative), which the probe never reads. A folder is on a mounted volume when it is inside `/Volumes`, in any case, by its name once `..` is undone or through a link; the probe checks each name before it reads that name's link, so it never looks inside `/Volumes` to find out, and git is handed the folder with its links followed. A folder whose repository points git inside `/Volumes` counts the same: its `.git` file or link, `commondir`, a chain of `objects/info/alternates`, or a config include or `core.worktree`, in any git folder from the folder up to `/`, and one the probe cannot read for sure counts as a volume. While git is held, a row keeps the branch and repository last seen; a folder git may not read clears both. A row written by an older probe has no `repository` key at all. Only the two names are published, never the remote's URL, a user name or token in it, or a path.

`branch` is that folder's current branch, read with `repository`. It is empty when the folder is outside any repository or on a detached head, which is correct, not a gap. The folder is where the agent process runs, or, for Codex, the folder its `-C` or `--cd` option names. An agent started in the home folder, or in a folder that holds several clones, is outside any repository even when it edits files inside one, so its row has no branch or repository; start the agent in the repository's own folder or worktree for its row to carry both. On the owner's Mac in October 2026 that was why most rows had no branch: 20 of 31 running Claude panes ran in the home folder and 5 more in folders holding clones, and every Codex session ran in a folder of clones or the home folder.

The fields above are contract 1.1 of `log.json`, which added `repository`. The file's `version` stays 1, since every 1.0 field is unchanged and a 1.0 reader passes over the new key.

Start means the first time the probe saw the session working. `done` means a finished turn. Close means the pane disappeared or its agent process exited. A failed machine read keeps its rows, with `stale` set, and says why under `problems`, keyed by machine. A read that answered can still name something it could not read there, such as a folder macOS held. Consumers also compare `as_of` with their clock and reject figures older than 90 seconds, including when the app has quit.

## How long a row stays

An open session stays as long as it is open. A closed session stays for 24 hours after its `closed_at`, then leaves `log.json`; nothing is summarised or archived.

The whole file has a budget of 2,000 rows and 2,000,000 bytes, half of what a reader accepts (5,000 rows and 4,000,000 bytes), shared evenly by the machines in `seats.json`: with four machines, each keeps 500 rows and 500,000 bytes, less its machine ID on each of those 500 rows. A machine's share holds all its open sessions, which are never dropped, then its newest closed sessions, newest first, up to the first that does not fit. A row's bytes are measured as `log.json` writes it, without the `machine` and `stale` fields the app adds, so the probe and the app measure it alike; the ID taken off the share pays for the machine field. `problems` keeps each machine's text to its first 1,000 characters and, in machine ID order, only the machines that fit within 200,000 bytes. The rest of what a reader accepts covers any open sessions past a share. Past 2,000 machines, or with a machine ID long enough to use up its share, a machine keeps its open sessions and no closed ones.

Each round the app sends every machine's probe its share as `log-probe --keep-rows <rows> --keep-bytes <bytes>`. The probe takes only whole numbers from 0 to the whole file's budget and passes over any flag it does not know; with no share, or one it refuses, it keeps the whole file's budget. The app applies the same rule to the rows it gets back, which changes nothing for a probe of this version and bounds a probe from an older one, and to the rows it keeps for a machine that did not answer. The share comes from the configured machines alone, so a second app or `seatgauge-cli log` on the same config, a restart or a failed write cannot move it.

The share trims only what the probe prints. The machine's private ledger and checkpoint drop a session only by the same rule with the whole file's budget, 2,000 rows and 2,000,000 bytes, the most any caller's share can be, so when two apps with different numbers of machines read one machine, the one with the smaller share deletes nothing the other would show (issue #131). A remote machine's helper from an earlier version still trims its ledger to the share until it is updated. A session that leaves the ledger and checkpoint is never read again. A session resumed after that shows as a new row, with the whole transcript counted; one the share hid but the ledger kept comes back with its totals when a larger share asks for it.

## Remote machines

The SSH machine needs the same version of the CLI helper and herdr at `~/.local/bin/herdr`. After `make install`, run:

```sh
scripts/install-log-probe.sh <ssh destination>
```

This installs only the helper at `~/.local/libexec/seatgauge-log-probe`. It uses the existing SSH login, without a password prompt. Repeat after upgrading the app. A missing helper shows up as a Log problem.

## Folder access on this Mac

The local probe runs inside the app, so macOS asks the app, not a terminal, whether it may open Desktop, Documents or Downloads, where many sessions work. The app is signed ad hoc, so every reinstall asks again. While that prompt is unanswered, macOS holds each read in the folder. The probe gives each `git` read of a branch or remote 2 seconds, and reads each folder once a pass; when one is held, it skips `git` for the rest of the pass, keeps the branches and repositories it last saw, and reports a folder-access problem for this Mac. A whole pass that runs past 90 seconds on this Mac is reported the same way rather than as a missing helper. Answer the prompt, or allow Seat Gauge in System Settings > Privacy & Security > Files and Folders. Over SSH no prompt appears, so neither case arises on a remote machine.

## Collection and privacy

The probe uses herdr pane and process information, then `lsof -b` on each agent PID. Codex can hold several rollouts, forks included. Each file has one owner and contributes once. Claude can report its session through herdr. Otherwise the probe matches its profile, working folder and file creation time within two minutes of process start. An ambiguous match keeps tokens pending.

The machine-local helper uses the Spend parsers and keeps, for each file, only what resumes its read: a byte offset and running totals by model, plus, for Claude, a 64-bit digest of each message the file counts, and for Codex, the file's first usage event, what it adds after that and the total it ends on. A partial line waits until it is complete. Each Claude message ID counts once: a message two files share counts in the file that read it first, and moves to another file that holds it once the first no longer does. Codex resumes use Spend's first-token ordering, including across read budgets, with a separate baseline for each forked session ID. A Codex file whose later events carry a usage field its first did not cannot be resumed from that first event alone, so when it follows another file of its session its usage lines are read again from the file, as Spend reads them; the checkpoint never keeps its events. The one exception is such a file in a checkpoint written by an earlier version: it keeps the events it had, untouched, until its session leaves. A Claude file that passed a message by because another file counted it names that file, and is read again from its start, keeping what it counts, when that file stops counting anything. A checkpoint written by an earlier version, which kept every response, is rewritten in this shape on its first pass, with the same totals and nothing read again.

Seat Gauge decodes only usage metadata from the log records it needs, and never inspects, keeps or sends message content. The public file contains no transcript paths, process arguments, prompts, or commands. Each machine keeps its pane observations in the private `log-private/observations.jsonl`, with a replaceable `offsets.json` checkpoint beside it. A pass appends a line only for a session that changed; an open one is also written every ten minutes, so a row that goes stale says about when it was last seen, and when another session of the same process is written, so the ledger keeps which of them was seen last. Once the file holds more than four lines per session (and more than 256), or a session has left under the rule above, it is rewritten as one line per session, the last each one had. Every pass deletes any `observations-before-compaction-<time>.jsonl` copy an older version kept beside the ledger. The directory is owner-only, and the files use mode 600. If you delete the checkpoint, the helper rebuilds token totals from the source logs, while the ledger keeps pane history. Keep the ledger if you want observations to outlast their panes.
